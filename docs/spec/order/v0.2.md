# chef order

ライフネットスーパーへの自動発注機能の仕様。`/chef` skill に `order` ドメインを新設する。

v0.1（`cart` 構想のブレインダンプ）からの確定版。実装中に仕様変更が必要になった場合は v0.3 を作成し、達成までそちらをメンテナンスする（v0.2 との差分を残すため）。

## 背景

現在は `/chef buy` で applied 済み献立から買い物リスト（テキスト）を生成できる。
これをネットスーパー「ライフ」のカートに自動投入できるようにする。決済は行わない。

## 前提

- このプロジェクトへの機能追加として実現する
- ブラウザ操作は **Playwright MCP**（AI 主導）で行う
- プログラミング言語は Ruby

## 世界観 / コマンド命名の根拠

レストランの Chef は買い物に行かず、仕入れ業者に**発注（order）**する。
主語が Chef なので「Chef が order するもの＝材料」で一意に定まる。

- `buy` … シェフ本人が買い物に行く感が出るため不採用
- `shop` … 名詞的・「店」感で主語がズレるため不採用
- `cart` … カートの中身を見る（show）感、動作が中途半端なため不採用
- **`order`** … 厨房から業者に発注をかける構図にはまる。短く誰でも知る動詞で綴りに迷わない

コマンドは `order`、キャラの口では「発注しとくね」「仕入れリストはこれ」と喋らせ、世界観を二重に効かせる。

## コマンド体系（`order` ドメイン新設）

| コマンド | 動作 | 状態 |
|---|---|---|
| `/chef order` | ライフのカートに発注（カート投入＋配送枠確保）＝**今回の中心** | 新規実装 |
| `/chef order list` | 仕入れリスト表示（現 `/chef buy` を rename・移管） | 既存流用 |
| `/chef order settlement` | 決済・購入確定 | **将来**（今回やらない。器だけ確保） |

- 引数なし `/chef order` が主動作（カート投入）。`plan` が引数なしで提案を始めるのと同じ作法
- `chef.md` ルーターに `order` を追加。`buy` は `order list` に寄せる（後方互換で `buy` を残すかは実装時判断）
- README フェーズ5（`shop *` 予約）を `order` 系に更新

## 設定の一本化

環境別の設定値（認証参照・カレンダーID）を 1 ファイルに集約する。skill を共有する可能性があるため、実値・参照を git に乗せない。

```
config/
  chef.local.yml          # gitignore（実値。各自が用意）
  chef.local.yml.example  # commit（雛形。構造を共有）
```

`config/chef.local.yml`（git 外）の例:

```yaml
calendar_id: "ktmt.ryo@gmail.com"
life_netsuper:
  op_item: "op://Personal/<item-id>"   # 1Password の item 参照
```

- `.gitignore` に `/config/*.local.yml` を追加
- 設定読み込みヘルパ（Ruby）を追加し、`calendar_id` / `life_netsuper.op_item` を yaml から返す
- **コード・spec・skill に item id / calendar_id を直書きしない**
- 認証の実値（パスワード）は 1Password にのみ存在。git に乗るのは参照すら無い `.example` だけ
- 既存の `calendar_id`（現状 `household` テーブルの key-value 行）を config 参照へ移行する。`meal-planning/SKILL.md` の参照元記述を `household` → `config/chef.local.yml` に書き換える。household の該当行は放置でよい（参照されなくなるだけ）

### 認証情報の動線

1. config の `life_netsuper.op_item`（例 `op://Personal/<item-id>`）を読む
2. `op read "<op_item>/username"` / `op read "<op_item>/password"` で取得
3. Playwright MCP でログインフォームに入力

> 注意: MCP がブラウザを AI 主導で操作する構造上、`op read` で取得したパスワード値はブラウザ入力の過程で会話ログ（context）を一時的に通る。git には残らないが transcript には出る。個人ツールとして許容する。

## 役割分担

- **Ruby スクリプト**: 発注対象リストの JSON を出力するのみ（既存 `shopping.rb` を流用。category=`調味料` には除外フラグを付ける）
- **Playwright MCP（AI）**: ブラウザ操作すべて（ログイン・配送枠確保・検索・カート投入判定・完了報告）
- script からブラウザは操作しない（MCP と同一ブラウザの二重操作はできないため）

## 処理フロー（`/chef order`）

1. **発注リスト取得**: `shopping.rb` から 肉魚 / 野菜 / その他 を投入対象として取得。`調味料` は別枠（在庫確認リスト）に回す
2. **ログイン**: config の `op_item` → `op read` で認証情報取得。ログイン済みなら配送ページへ、未ならログインページ（https://www.life-netsuper.jp/introduction/login）からログイン
3. **配送枠確保**（ライフの仕様上、注文前に必須）: 配送予約ページ（https://www.life-netsuper.jp/delivery_select）を開き、予約可能な時間枠を提示 → 対話で選択
4. **カート投入**: 商品ごとに検索 →
   - 候補が 1 つ → 投入（数量 1 固定）
   - 候補が複数 → 対話で選択（グラム数違い等。検索品以外も出るため AI 判定が肝）→ 投入（数量 1 固定）
   - 候補なし → 一旦スキップし、最後にまとめて報告
5. **完了報告**（出力のみ・DB 保存なし）:
   - 追加できた → 商品名を出力
   - 候補なし → 項目名を出力
   - 調味料（在庫確認枠）→「家にある？切れてたら手で足してね」と確認リストを出力

## 数量

- 全商品 **1 個固定**（DB に数量データがないため）

## やらないこと

- 決済・購入確定（`order settlement` は将来）
- カートの数量を考慮した投入
- 調味料の自動投入（在庫確認リストに回す）
- 発注履歴の DB 保存（ライフ側の購入履歴で代替できるため）
