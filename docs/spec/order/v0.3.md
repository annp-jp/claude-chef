# chef order — v0.3（実機検証で判明した実装課題と確定方針）

v0.2 の設計方針はそのまま。本ドキュメントは 2026/05/31 にライフネットスーパー実機で
`/chef order` フローを通した検証で判明した **サイト固有の壁と、その確定対処** を追記する。
v0.2 との差分を残すための作業ドキュメント（達成までここをメンテする）。

検証条件: 希望が丘店 / 配送枠 6/1(月) 18:00〜20:00 / applied 献立 week_start=2026-06-01。
ログイン→配送枠確保→検索→カート投入→報告まで全段通過。最終的にカート15点投入。

---

## 結論（最重要）: 操作は vision-first にする

ライフは **Flutter Web 製**。canvas に描画され、通常の DOM / shadow DOM では要素が取れない。
さらに **アクセシビリティ（semantics）ツリーが画面（canvas）と同期しない**ことが実機で確定した。

### semantics ツリーは信頼できない（確証）

`鶏ささみ`『ひき肉』『豚肉』検索で、semantics ツリーには **在庫なしの旧バリアントしか無く**、
**実際に画面に出ている在庫ありの生鮮（グラム売り等）が1件も存在しない**状態を確認した。
人間が見る画面（スクリーンショット）には在庫ありが正しくトップ表示されているのに、
自動操作が読む semantics は別物（古い/部分的）を返す。これが「在庫なしと誤判定」の真因。
→ サイトの関連順ソートや在庫の問題ではなく、**semantics と canvas の desync** が原因。

### 確定方針: スクリーンショットで読み、座標でクリックする

- **読む**: `browser_take_screenshot` で画面を撮り、**目視（vision）で商品・価格・在庫・＋ボタン位置を判断**する。
  canvas は人間が見るものと一致するので、これが唯一信頼できる情報源。
- **クリック**: `browser_run_code_unsafe` の `page.mouse.click(x, y)` で**実ポインタ座標クリック**。
  Flutter が実ポインタイベントとして処理する。semantics の node-id クリックには依存しない。
- 実機で `鶏ささみ`(若どりささみ200g) と `ひき肉`(豚挽肉110g) を vision-first で投入成功。
  semantics 方式では両方「在庫なし」と取りこぼしていた。

### semantics / DOM は補助的に併用してよい

- 検索ボックスは DOM 実体 `input[aria-label="商品を検索"]` が安定。`fill` + `Enter` で検索。
  （semantics の ref はカート点数が変わるたび失効するので使わない）
- ログイン画面のフォーム入力は semantics 経由でも動いた（後述）。要素が取れる画面では使ってよい。
  取れない/古い疑いがあれば即 vision に切り替える。

## ログイン（確定挙動）

1. semantics 有効化が必要な場合がある: `document.querySelector('#enable_accessibility')?.click()` を
   `browser_evaluate` で実行 → 約2秒で要素ツリー生成。**フルページ遷移のたび無効化**される。
2. `/introduction/login` でメール/パスワードを入力。認証情報は
   `op read "$(ruby scripts/config.rb life-op-item)/username"` /`.../password` で都度取得。
3. **ログインボタンは1回目クリックが無反応のことがある**。click 後に URL が `/`（トップ）へ
   変わらなければリトライ。成功判定 = URL が `/introduction/login` → `/`。

## 配送枠（確定挙動・v0.2通りで正しい）

- トップ左「受け取り日時 未設定『設定する』」→ `/delivery_select`。
- 当日枠は受付終了が多い。翌日以降の `受付中` 枠を対話で提示して選ばせる。
- 枠選択 →「受け取り日時を設定」で確定。設定後 **1時間ホールド**。
- 枠確保前はカートに進めない仕様 → 「配送枠を先に確保」は必須で正しい。

## カート投入（vision-first 手順）

1. `input[aria-label="商品を検索"]` に食材名を `fill` + `Enter`。
2. `browser_take_screenshot` で結果を撮る。**全商品が描画されるまで必要なら待つ**。
3. スクショを目視し、対象食材に合う**在庫あり**商品を選ぶ（価格・グラム・形態を見て判断）。
4. その商品の緑「＋」ボタンの座標へ `page.mouse.click(x, y)`。
5. 再スクショでカート点数・数量バッジの増加を確認。
6. 数量は1。**同じ座標を二重クリックしないよう注意**（検証中、誤って数量2になった事例あり）。

## 検索・候補判定の実態（AI判定が要るポイント）

- **検索が曖昧で関連商品を返す**: `白菜` でキャベツ・小松菜が混在。商品名で要フィルタ。
- **ペットフード混入**: `鶏ささみ` 上位に犬猫用（ちゅ〜る等）。`犬用|猫用|ちゅ〜る|ペットフード|ピューレ` 等を除外。
- **「在庫なし」と即断しない**: semantics desync の影響で在庫ありを見落とす。必ずスクショで確認してから結論づける。
- **生鮮はグラム売りが主**: 在庫ありの生肉はグラム売り（例「国内産豚肉こま切れ190g ¥281目安」）。
  パック版は在庫なしのことが多い。スクショで在庫ありを拾う。
- **DBの材料名が曖昧/料理名のことがある**: `魚（何か）`『なんらかの具』『ひややっこ(冷奴)』等。
  → これは献立生成（chef plan）側のDB品質問題。order スコープ外で別途対応。

## 選択は「対話前提」に倒す（方針変更）

v0.2 は「18品を毎回聞くと遅い」として AI 自動選択寄りだったが、**誤選択の入れ替えコスト > 確認コスト**
と判明したため、**各品ユーザーに確認する**方針へ変更する。確認を的確にするため、
判断材料として「**その材料がどの料理に使われるか**」を提示する。

例（実フィードバック）:
- きゅうりは4本も要らない（パックサイズの希望がある）
- うずら卵は「6個入×2」が欲しい（規格指定）
- 肉団子はスープ用 → 味付き不可・素のもの希望。冷凍なら余りが日持ちして良い
- 餃子は30個入りが欲しい

### 実装: shopping.rb の出力に「使用料理(dish)」を付ける

各材料がどの recipe（料理名）で使われるかを JSON に含め、order 側の選択提示のヒントにする。
→ **実装済**。`shopping.rb` の各 item に `dishes: [料理名,...]` を追加。
