# Chef - 我が家の献立シェフ 仕様書

## 概要

我が家の夕飯の献立を考えてくれるシェフ。Claude Code上で `/chef` スラッシュコマンドとして動作する。

レシピマスタの管理、1週間の献立提案、買い物リスト生成、ネットスーパー連携までを統合的に扱う。

## 設計思想

### 世界観

`/chef` は「我が家のシェフ」というドメインメタファーで設計されている。コマンド名はこの世界観に揃える（`init` ではなく `onboard`、`config` ではなく `brief`）。

### スコープ

**v1で扱う**: 平日夜の夕飯（dinner）のみ

**将来拡張余地**: 朝食・昼食、ネットスーパーのカート自動投入、配達枠予約

朝昼を将来扱えるよう、スキーマには `meal_type` 列を持たせておく。ただしv1の実装・コマンドは dinner 前提で動く。

### アーキテクチャ

- 実行環境: Claude Code（スラッシュコマンド `/chef`）
- データストア: SQLite（プロジェクトローカル）
- 外部連携: Googleカレンダー（献立確定時）、LIFEネットスーパー（特売閲覧から段階的に）

スマホからの記録は v1 では非対応。PCから `/chef log` で記録する。必要性が顕在化したら別所（Googleスプレッドシート等）への inbox 機構を追加する。

### 設計上のトレードオフ判断

- **SQLite vs スプレッドシート**: SQLiteを選択。「直近N週間で登場してないレシピ」「主菜×副菜の組み合わせ候補」のような献立生成クエリがSQLで書きやすく、挙動のブレが抑えられる。スプレッドシートはスマホアクセスの利点があるが、献立生成の精度・確実性を優先した
- **`plan` と `plan apply` の分離**: 副作用（Googleカレンダー登録）が走る操作は明示的に分離。提案フェーズは何度でも試行錯誤でき、確定は意図的な1コマンド
- **コマンド命名**: 動詞性を揃える。世界観に寄せる遊び（onboard, brief）と実用性（study, plan, log）のバランスを取る

## コマンド体系

### 初期設定（世界観優先）

```
/chef onboard                  # シェフを我が家に迎え入れる（DB初期化、brief雛形作成）
/chef brief                    # 指示書を渡す（家族・アレルギー・ルール編集）
```

### レシピマスタ

```
/chef study [URL]              # レシピを覚えさせる（対話 or URL抽出）
/chef menu [filter]            # 覚えているレシピ一覧・検索
```

`study` はURL指定時はWebFetchでレシピサイトから材料・手順を抽出し、確認を経て登録。URL省略時は対話形式で項目を埋めていく。

`menu` のフィルタは自然言語で受け付ける（例: `/chef menu 卵を使った主菜`）。

### 献立計画

```
/chef plan                     # 来週の献立提案（対話で調整）
/chef plan apply               # 確定 → Googleカレンダー登録 + DBに保存
```

`plan` は対話的に提案・修正を繰り返せる。要望（制約・希望）は自然言語で受け付ける。

`apply` は副作用を伴う不可逆操作。実行前に最終確認を入れる。

### 記録

```
/chef log <料理名> [--date YYYY-MM-DD]    # 「今日これ作った」を記録
```

`plan apply` で予定登録した献立は自動的に `meal_log` に記録される想定だが、実際の調理が予定と異なった場合のために手動補正用のコマンドとして用意。

### 買い物

```
/chef buy                      # 直近の確定献立から買い物リスト生成
```

カテゴリ別（肉魚 / 野菜 / 調味料 / その他）に整形して出力。

### ネットスーパー連携（段階的）

```
/chef shop sale                # 特売閲覧（フェーズ4）
/chef shop login               # ログイン（フェーズ5）
/chef shop cart                # カート投入（フェーズ5）
```

LIFEネットスーパーを当面の対象とする。`shop` という汎用名にしておくことで、将来他のスーパーに切り替わっても意味が崩れない。

## データモデル

### `recipes`

レシピのマスタ。

| 列 | 型 | 説明 |
|---|---|---|
| id | INTEGER PK | |
| name | TEXT NOT NULL | 料理名 |
| type | TEXT | 主菜 / 副菜 / 汁物（複数可、JSON配列） |
| meal_type | TEXT | dinner / lunch / morning（v1は dinner固定） |
| ingredients | TEXT | 材料（JSON配列、各要素 `{name, amount, category}`） |
| instructions | TEXT | 手順（任意） |
| url | TEXT | 参照元URL（任意） |
| kids_ok | BOOLEAN | 子供向けOKか |
| allergens | TEXT | 含むアレルゲン（JSON配列） |
| cook_time_min | INTEGER | 調理時間目安（分） |
| note | TEXT | メモ |
| created_at | DATETIME | |

### `meal_log`

実際に作った料理の記録。重複回避（先週も食べた防止）の参照元。

| 列 | 型 | 説明 |
|---|---|---|
| id | INTEGER PK | |
| date | DATE NOT NULL | |
| meal_type | TEXT | dinner固定（v1） |
| recipe_ids | TEXT | JSON配列。主菜・副菜の複数を持ちうる |
| note | TEXT | |

### `meal_plans`

確定済み献立のアーカイブ。`plan apply` で書き込まれる。

| 列 | 型 | 説明 |
|---|---|---|
| id | INTEGER PK | |
| week_start | DATE NOT NULL | 週の月曜日 |
| status | TEXT | draft / applied |
| plan_json | TEXT | 日付ごとの献立構成（JSON） |
| applied_at | DATETIME | カレンダー登録した時刻 |

### `household`

家族構成・全体ルールの初期設定。kv形式。

| 列 | 型 | 説明 |
|---|---|---|
| key | TEXT PK | members, dietary_notes, weekly_pattern_hint など |
| value | TEXT | 自由記述。献立生成時に参考情報として渡される |

例:
- `members`: `リョウ(1986/大人), 配偶者(大人), 子A(2020/子供)`
- `dietary_notes`: `子供は薄味希望、辛い物NG`
- `weekly_pattern_hint`: `平日は時短重視、金曜は少し凝ったもの可`

### `allergies`

アレルギーと苦手食材。**献立生成のハードフィルタ**として機能するため、構造化して厳密に扱う。

| 列 | 型 | 説明 |
|---|---|---|
| id | INTEGER PK | |
| food | TEXT NOT NULL | 対象食材 |
| member | TEXT NOT NULL | 対象メンバー |
| severity | TEXT NOT NULL | `アレルギー` / `苦手` |
| note | TEXT | |

ロジック:
- `severity = アレルギー` → 該当食材を含むレシピは**絶対に提案しない**（ハードフィルタ）
- `severity = 苦手` → できるだけ避ける（ソフトフィルタ）

### `rules`

曜日ルール（月曜は魚、水曜は麺類など）。

| 列 | 型 | 説明 |
|---|---|---|
| id | INTEGER PK | |
| day_of_week | INTEGER | 1=月 〜 7=日 |
| rule_type | TEXT | category / time_constraint など |
| content | TEXT | ルール内容 |
| priority | INTEGER | 競合時の優先度 |

## ワークフロー例

### 日曜夜: 来週の献立決め

```
リョウ: /chef plan
Chef:   来週（M/D〜M/D）の献立を提案するね。
        直近3週間の履歴を確認、家族のアレルギー（卵：完全除去）を反映、
        曜日ルール（月=魚、水=麺）も考慮した提案:

        月: 鮭の塩焼き + ほうれん草のおひたし + 味噌汁
        火: 肉じゃが + 冷奴
        水: 鶏南蛮うどん + 小鉢
        木: ハンバーグ（子供OK）+ サラダ
        金: 豚の生姜焼き + キャベツ千切り

        要望ある？

リョウ: 火曜は早く帰れないから時短で
Chef:   火曜を変更。肉じゃが（45分）→ 鶏ももの照り焼き（20分）+ 冷奴。
        他はこのままでOK?

リョウ: OK

リョウ: /chef plan apply
Chef:   Googleカレンダーに5件登録、meal_plansに保存しました。
```

```

        - 豚ロース 4枚
        - 牛切り落とし 200g
        - 合挽き肉 400g

        ...
```

### 平日夜: 記録（必要に応じて）

```

```

## 開発フェーズ

機能を一気に作らず、段階的に育てる。

### フェーズ1: データ基盤

実装: `onboard`, `brief`, `study`, `menu`, `log`

ゴール: レシピマスタが構築でき、日々の調理を記録できる状態。

検証ポイント: スキーマが実用に耐えるか、レシピ登録のUXが快適か。20〜30品登録して数週間運用する。

### フェーズ2: 献立生成

実装: `plan`, `plan apply`（Googleカレンダー連携込み）

ゴール: 履歴・アレルギー・ルールを統合して献立を提案できる。

検証ポイント: 提案の質、対話的な修正のしやすさ、カレンダー登録の正確性。

### フェーズ3: 買い物リスト

実装: `buy`

ゴール: 確定献立からカテゴリ別の買い物リストが生成される。LIFEのカテゴリ順に整理しておくと将来連携が楽。

### フェーズ4: 特売情報

実装: `shop sale`

ゴール: LIFEネットスーパーの特売ページを取得し、献立提案時に「特売品優先で」の指示を反映できる。

検証ポイント: スクレイピングの安定性、構造変更への耐性。

### フェーズ5: カート自動投入

実装: `shop login`, `shop cart`

ゴール: Claude in Chromeで認証突破 + 配達枠予約 + カート投入。

このフェーズは認証・配達枠・在庫変動など外部依存が多く難度が高い。フェーズ4までで日常運用は完成しているため、ここは「あれば嬉しい」枠。

## スキル構成（実装側）

機能ごとにスキルを分割する。これによりコンテキストの肥大化を防ぎ、必要な機能だけが読み込まれる。

- `recipe-library`: レシピマスタ管理（`study`, `menu`）
- `meal-logging`: 調理記録（`log`）
- `meal-planning`: 献立生成（`plan`, `plan apply`）
- `shopping-list`: 買い物リスト生成（`buy`）
- `super-deals`: ネットスーパー連携（`shop *`）

各スキルは独立して呼び出し可能。`meal-planning` は他スキルを内部的に参照する（recipes、meal-log、household、allergies、rules）。

## 残課題・将来検討

- スマホからの記録方法（必要になったら検討）
- 主菜・副菜の組み合わせロジックの精緻化（最初はシンプルに、運用しながら調整）
- 食材の在庫管理（買ったのに作らなかった、余ってる、等）— v1スコープ外
- 栄養バランスの考慮 — v1スコープ外
- レシピサイトのスクレイピング対応範囲（クックパッド、デリッシュキッチン等、サイトごとに構造異なる）
